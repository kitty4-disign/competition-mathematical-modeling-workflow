# 子问题模块路由与结果链管理

## 目的与边界

将多问竞赛题拆成**最小必要的工作模块**，避免还未明确任务就同时调用所有分析、预测、仿真和写作流程。模块仅规定工作顺序、输入输出和验收门槛，不替代题意理解、模型选择或人工审查。

本参考用于题意拆解完成后、正式计算开始前。在 `assets/templates/workflow-ledger.md` 中为每个子问题建立任务行；同一时点最多启用 1–3 个最相关模块。只有当新的数据、约束、失败诊断或验证需求出现时，才扩展模块并新增决策 ID。

## 模块路线卡

| 模块 | 适用信号 | 最低输入 | 退出产物与门槛 |
|---|---|---|---|
| 问题规格 | 多问题、边界不清、交付格式严格 | 题目、附件、规则 | 需求矩阵、变量/约束初稿、依赖图、假设清单。 |
| 数据审计 | 有题目数据、外部数据或多表数据 | 原始文件与字段说明 | 数据字典、质量报告、清洗规则、可复现预处理路径。 |
| 探索与基线 | 需要判断模式、规模或可行性 | 已审计数据或小规模实例 | 描述性结果、基线方案和待解释异常。 |
| 数学规格 | 需要模型、算法或决策规则 | 子问题目标、数据边界、验收标准 | 候选比较、公式—题意映射、变量域、求解与验证计划。 |
| 优化/预测/机制求解 | 已有可执行数学规格 | 公式、参数、输入版本和基线 | 求解状态、结果工件、运行配置和失败/近似说明。 |
| 随机仿真 | 随机需求、风险、个体交互或情景传播是核心 | 随机机制、分布/边界、确定性基线 | 读取 `simulation-uncertainty-experiments.md` 后形成收敛与风险结果。 |
| 验证与反例 | 已有初步结果或结论 | 结果工件、基线、验证切分/情景 | 证据矩阵、稳健性结论、失败情景和适用范围。 |
| 图表与论文 | 关键计算已冻结 | 结果工件、图表、引用与任务映射 | 题目要求—方法—结果—验证—图表/表格映射与可追溯稿件。 |

## 路由程序

1. 为每个子问题编号，并将其要求、直接上游、验收标准和预期结果 ID 写入工作台账。
2. 选择 1–3 个最小必要模块，声明每个模块的输入版本、预期产物和退出门槛。
3. 先完成问题规格与数据审计，再进入探索、数学规格或计算；不能以“后续会补”跳过影响模型选择的门槛。
4. 模块输出只要影响下一模块，就分配结果 ID，并在台账中记录生成脚本、参数/种子、验证位置和直接依赖。
5. 出现无解、未收敛、数据泄漏、明显不稳或证据冲突时，停止向下游写作传播；按 `verification-and-repair.md` 回退到执行、实现、规格或问题定义层。
6. 计算冻结后，检查每一项赛题要求是否都映射到至少一个方法、可复算结果、验证项和正文/图表位置；缺项不能以泛化描述替代。
7. 任一上游输入、规格、代码或参数变化时，将依赖它的结果、验证、图表和主张标为 `stale`，重算后再冻结。

## 共享结果与版本纪律

将同一结果的代码、表格、图和正文结论绑定到一个结果标识。例如，`R-T2-forecast-v3` 应在运行日志、结果文件名、验证表和论文中保持一致。修订模型、数据、参数或筛选条件后，创建新版本；不要让新图表继承旧结论，也不要让同一数值在不同文档中靠手工复制维护。

论文、Word、PDF 或其他交付格式应由同一经审阅的源稿与同一结果工件生成；导出后检查页码、图表、公式、引用和数值一致性。任何格式转换失败或导出后内容变化，都必须修复源稿并重新导出，而不是分别手工修补多个版本。
